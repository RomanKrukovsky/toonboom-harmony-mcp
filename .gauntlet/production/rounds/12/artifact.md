# Раунд 12 — возобновление после аварии — линза: operability

Вопрос линзы: **человек, не писавший этот код, восстанавливает серию после
аварии по документации. Смотреть на то, что он видит в терминале.**

Проиграл этот путь буквально: настоящий `kill -9` посреди прогона, потом та же
команда, как велит `PRODUCTION.md`. Blender 5.1.1, commit c8f3c3f.

## Что работает

Восстановление по документации **проходит**. Оператор запускает ту же команду и
получает досчёт:

```
$ python3 episode.py --demo --shots 12 --frames 8 --out /tmp/op13
episode: demo — 12 shots, 96 frames, 4.0s
preflight: ok (~0.01 GB needed, 46.13 GB free)
start: 0 shots to render (12 already done), 12 workers
```

Строка `start:` отвечает на главный вопрос утра — сколько уцелело. Замок прогона
сообщает, кто держит серию, и снимается сам после `kill -9`. Мастер называет
дыру, если серия неполная (раунд 10). Кадр отвечает, какой прогон его сделал
(раунд 11). По существу восстановление операбельно.

## Дефект 1 — прогресса не существует, есть отчёт

Замер: время появления строки в выводе против времени события.

```
    0.2s  episode: demo — 12 shots, 96 frames, 4.0s
    0.2s  preflight: ok (~0.01 GB needed, 43.95 GB free)
    0.2s  start: 12 shots to render (0 already done), 12 workers
    7.3s    ok   sc001  1/12  3.96 fps, eta 22.2s
    7.3s    ok   sc009  2/12  2.6 fps, eta 30.8s
    7.3s    ok   sc006  3/12  3.81 fps, eta 18.9s
    ... ещё 9 строк — все на 7.3s
    7.3s  rendered 96 frames in 6.63s (14.48 fps), 0 failed
```

**Одиннадцать строк прогресса вываливаются одной пачкой в конце.** Внутри
конвейера события идут по мере готовности шотов — `frames_per_s` в них растёт
3.96 → 14.55, то есть моменты разные. Наружу они не выходят: `print` буферизуется.

Это не косметика, потому что бьёт ровно по ночному прогону из документации.
`PRODUCTION.md` предлагает `> /tmp/night.log`, а в файл Python буферизует
блоками, не строками. Замер на ночном прогоне 14 шотов:

```
  время → строк в логе:
      0.5s  3
     11.1s  19
```

**10.6 секунды лог не меняется**, потом 16 строк сразу. На серии 22 минуты
(~45 минут счёта) это `tail -f` по пустому файлу почти всю ночь. Оператор не
может отличить работающий конвейер от зависшего — а это первое, что он проверяет,
проснувшись.

Хуже: `eta` в строках посчитана верно (22.2s → 12.6s → 3.3s), но приходит, когда
всё уже кончилось. Прогноз, доставленный после события, — не прогноз.

## Дефект 2 — «1241336 fps» в отчёте

Когда досчитывать нечего (серия уже готова), итог выглядит так:

```
start: 0 shots to render (3 already done), 12 workers
rendered 12 frames in 0.0s (1241336.38 fps), 0 failed
```

Два неверных утверждения в одной строке. **Ничего не отрендерено** — 12 кадров
взяты из журнала прошлого прогона, а не посчитаны сейчас. И скорость миллион
кадров в секунду — деление на округлённый до нуля интервал.

Для оператора это ровно тот же класс, что «+-1%» в раунде 7 и `master: 1.523s`
над дырявой серией в раунде 10: число верное по арифметике, вывод из него
сделать нельзя. Здесь хуже — число не просто нечитаемо, оно утверждает работу,
которой не было. Человек, впервые запустивший конвейер дважды, вправе решить,
что второй прогон всё пересчитал.

## Дефект 3 — молчание там, где нужен ответ

При нуле работы конвейер не говорит главного: **серия уже готова, делать нечего.**
Он печатает `0 shots to render` мелким шрифтом среди служебных строк и
фальшивое «rendered 12 frames». Прямой фразы нет.

## Итог по линзе

Путь восстановления — операбелен: одна команда, учёт уцелевшего верен, ошибки с
указанием действия. Обратная связь **во время** работы — нет: прогресс не
доставляется, а итог при пустом досчёте вводит в заблуждение.

Разница между «конвейер работает» и «оператор видит, что конвейер работает».
Для ночного прогона это и есть вся операбельность.
