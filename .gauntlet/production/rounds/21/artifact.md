# Раунд 21 — отчёт и прогресс для оператора — линза: resume

Вопрос линзы: **после kill -9 прогон продолжается с места остановки. Что
пересчитывается лишнего? Смотреть на замер «сколько работы пропало».**

На этой части вопрос другой: что отчёт ГОВОРИТ про досчёт. Blender 5.1.1,
commit 706882d.

## Отчёт не помнил аварию

Прогон 8 шотов, kill -9 после трёх, затем досчёт. Итоговый отчёт:

```
  ПОСЛЕ ПАДЕНИЯ: partial=True, ok 3/8, не начато 5
  ПОСЛЕ ДОСЧЁТА: partial=None, ok 8/8, resumed=3, rendered_now=30
  seconds=13.53
```

Три вопроса, на которые ответа не было:

| вопрос | ответ |
|---|---|
| сколько времени ушло ВСЕГО (оба прогона) | **нет в отчёте** |
| какие прогоны участвовали | **нет в отчёте** |
| была ли авария вообще | **нет в отчёте** |

`seconds=13.53` — время **последнего** прогона. Журнал шотов при этом знал, что
шоты от двух разных прогонов; отчёт этого не говорил. И `run.json` перетирался
каждым запуском, поэтому заявка упавшего прогона исчезала.

### Во что это обходится

Серия 314 шотов, упала на 200-м (30 минут работы), досчитана за 16:

```
  отчёт скажет:  seconds = 960 (16 минут), complete = true
  фактически:    46 минут машинного времени
  ошибка планирования: 2.9x
```

Оператор планирует следующую ночь по этой цифре — и получает вдвое-втрое
недооценённый бюджет.

Исправлено: `runs.jsonl` (дописывается, не перетирается) плюс в отчёте
`attempts`, `crashed_before`, `wall_seconds_total`, список прогонов. На том же
прогоне:

```json
{"attempts": 2, "crashed_before": 1,
 "wall_seconds_total": 47.53, "seconds": 23.07}
```

И в терминале, где оператор это увидит:

```
rendered 48 frames in 22.09s (1.36 fps), 0 failed
  this episode took 2 attempt(s): 50.6s of wall time in total (22.09s in this run)
```

## Метка прогона не различала прогоны

Регрессия падала в наборе и проходила в одиночку — признак зависимости от
состояния. Причина оказалась не в тесте:

```
  run_id = f"{int(time.time())}-{os.getpid()}"
```

Секунды плюс PID. **Два прогона в одну секунду из одного процесса получали
одинаковую метку.** Где это бьёт по существу:

- досчёт сразу после падения — оператор перезапускает мгновенно;
- CI, прогоняющий серию дважды;
- **раунд 11 обещал**, что серия после аварии склеена из шотов разных прогонов «и
  метка их различает». При быстром перезапуске — не различала.

То есть дефект был в механизме, который я в раунде 11 объявил закрытым, и нашёлся
только потому, что тест начал падать от порядка запуска. Теперь метка —
миллисекунды, PID и четыре случайных знака.

## Закрытие разрыва: граничные условия проверяются, а не всплывают

Дефект метки нашёлся **случайно** — регрессия начала падать от порядка запуска. То
есть механизм, объявленный готовым в раунде 11, три раунда жил с изъяном, который
снимается одним вопросом: «а если два прогона в одну секунду?».

Записано механически — `test_boundaries.py`, десять проверок, задающих каждому
механизму одни и те же вопросы:

| вопрос | что проверяет |
|---|---|
| два вызова подряд в одну секунду, один процесс | метка прогона различает |
| каждое поле, влияющее на кадр | отпечаток шота меняется от всех семи |
| две одинаковые записи подряд | хэши в цепочке различны |
| пустой ввод | `recover_report`, `run_history`, `_group_failures`, `verify` |
| один элемент | серия из одного шота не путается с нулём |
| вход с заранее известным неверным ответом | кадр за пределами мастера, подделка реестра |

Проверил обратным экспериментом: вернул старую метку — набор падает на
`test_run_id_differs_within_the_same_second`, код выхода 1. То есть проверка ловит
именно этот дефект, а не просто существует.

## Итог по линзе

Возобновление работало; отчёт о нём — нет. Серия, собранная за несколько попыток,
выглядела как посчитанная с первого раза, и цифра, по которой планируют ночь, была
втрое меньше фактической. Попутно нашлась неуникальная метка прогона — в той
части, которую два раунда назад я считал готовой.
