# Раунд 11 — возобновление после аварии — линза: traceability

Вопрос линзы на этой части: **после аварии мастер склеен из шотов, посчитанных
разными прогонами. Можно ли по кадру из готовой серии узнать, откуда он взялся?**

Замеры на живом конвейере (Blender 5.1.1, commit e22baba), не рассуждения.

## Проба 1 — команда из документации на настоящей серии

`PRODUCTION.md` обещает раздел «Кто сделал этот кадр» и даёт команду. Запустил её
на серии, посчитанной штатным путём:

```
$ python3 episode.py --demo --shots 2 --frames 4 --out /tmp/prov_probe
rendered 8 frames in 1.63s (4.92 fps), 0 failed
master: /tmp/prov_probe/master.mp4 — 0.356s, streams ['video', 'audio']

$ ls /tmp/prov_probe/
concat.txt  demo_parts  journal.jsonl  master.mp4  report.json  sc001  sc002
```

**`provenance.jsonl` в каталоге серии нет.** Команда из документации:

```
{"scene": "demo", "frame": 3, "verdict": "untracked", "styles_used": [], "touches": []}
```

`untracked` — на каждый кадр каждой серии, посчитанной конвейером.

Реестр происхождения работает: 44 теста, 314 шотов в раунде 6, три модели
подделки ловятся. Но `Ledger(` не вызывается **ни в одном** месте `episode.py` —
только в смоук-тестах и капчурах:

```
$ grep -rln "Ledger(" *.py
capture_trace.py  smoke_full_shot.py  smoke_traceability.py  test_provenance.py
```

То есть проверенный механизм не подключён к конвейеру, а документация обещает
обратное. Юридическая конструкция, на которую я в раунде 6 потратил раунд,
на настоящей серии не существует.

## Проба 2 — какой прогон сделал шот

Смоделировал ровно ту ситуацию, которую закрывает возобновление: прогон 1
считает два шота, авария, прогон 2 досчитывает остальные. Спросил журнал, чем
шоты отличаются:

```
  шот    поле «какой прогон»       факт
  sc001  НЕТ                      прогон 1
  sc002  НЕТ                      прогон 1
  sc003  НЕТ                      прогон 2
  sc004  НЕТ                      прогон 2

  поля записи: ['audio', 'dir', 'fingerprint', 'finished_at', 'frames',
                'name', 'seconds', 'status']
  версия Blender в журнале: НЕТ
```

Различить прогоны можно только косвенно — по разрыву в `finished_at`, и то если
знать, когда была авария. Идентификатора прогона в записи нет.

Почему это важно именно для возобновления, а не вообще: **прогоны идут в разных
условиях.** Между падением и досчётом мог обновиться Blender, мог поменяться
`BLENDER_BIN`, машина могла быть другой. Отпечаток шота (`fingerprint`) стережёт
изменения *описания* — тайминг, рисунки, звук, камеру, — и он не подозревает о
версии рендерера: тот же шот, посчитанный Blender 5.1 и 5.2, даёт одинаковый
отпечаток и считается готовым. Если серия разъехалась по виду на границе шотов,
журнал не отвечает, где разошлись условия.

## Что работает

- **Учёт готовности точен.** Отпечаток шота ловит правку тайминга без изменения
  длины (раунд 9): досчёт не соберёт серию по вчерашней версии.
- **Замок прогона** пишет PID и время старта, снимает мёртвый замок и сообщает
  об этом событием `stale_lock` — то есть *про сам прогон* трассируемость есть.
- **Мастер называет дыру** (раунд 10) и возвращает ненулевой код.
- Реестр происхождения как механизм проверен и цел — вопрос только в том, что
  его никто не вызывает.

## Итог по линзе

Трассируемость **процесса** — есть: журнал, отпечатки, замок, отчёт.
Трассируемость **кадра** — нет: обещанный документацией реестр не заполняется, и
принадлежность шота прогону/версии рендерера не записывается.

Для студии это разница между «мы знаем, что конвейер сделал» и «мы можем
ответить на претензию по конкретному кадру».
