# Раунд 20 — отчёт и прогресс для оператора — линза: resilience

Вопрос линзы: **что происходит при сбое — пропал файл, кончилось место, битый
рисунок? Ошибка называет причину и что делать? Смотреть на поведение под
настоящим сбоем.**

Четыре сбоя устроены руками. Blender 5.1.1, commit cf08706.

## После kill -9 отчёта не существовало

```
  kill -9 посреди прогона: report.json НЕТ, в журнале 2 шотов
```

`PRODUCTION.md` велит утром смотреть `report.json`, «а не закрытый терминал». Но
он пишется в конце прогона — то есть ровно в том случае, ради которого написан
(ночь упала), его нет.

Что оставалось утром: `journal.jsonl` — машинный формат без итога — и закрытая
сессия. Данные для ответа в журнале **были**, кроме одного: сколько шотов в
серии. Журнал знает только сделанные.

Лечение в два шага.

**Заявка прогона `run.json`, кладётся ДО счёта:** что прогон собирался сделать,
чем считает, каким прогоном.

**`recover_report()`** собирает итог из заявки и журнала. На настоящем падении:

```json
{"recovered": true, "run": "1786178686-53891", "renderer": "Blender 5.1.1",
 "shots_total": 8, "shots_ok": 1, "frames_rendered": 6, "frames_total": 48,
 "not_started": ["sc002","sc003","sc004","sc005","sc006","sc007","sc008"],
 "complete": false}
```

Помечен `recovered`, чтобы не выглядеть отчётом завершённого прогона. Обрубок
журнала от падения посреди записи отбрасывается — иначе авария лишает оператора и
последнего источника.

**Печатается при следующем запуске**, потому что оператор не знает про
`recover_report` и всё равно набирает ту же команду:

```
previous run did not finish (run 1786178686-53891, Blender 5.1.1):
  1 of 8 shot(s) rendered, 6 of 48 frames, 7 never started
  full recovered report: /tmp/rec20/report.recovered.json
```

## Два трейсбека вместо причины

| сбой | было | стало |
|---|---|---|
| каталог только для чтения | `PermissionError: [Errno 13]` **после счёта** | `[OUT_NOT_WRITABLE]` + что делать, до счёта |
| папка с именем `report.json` | `IsADirectoryError: [Errno 21]` | `[NAME_TAKEN]` + `Remove <путь>` |

Оба вылезали **после** того, как серия посчиталась: беда, видимая за секунду,
обнаруживалась через час. Тот же класс, что трейсбек вместо инструкции в раунде 8.
Теперь проверяются в preflight пробной записью и проверкой служебных имён
(`report.json`, `journal.jsonl`, `run.json`, `master.mp4`), код выхода 2.

## Что и так держалось

```
  битый report.json от прошлого прогона: код 0, отчёт перезаписан корректно: да
```

Отчёт не читается конвейером, только пишется, поэтому мусор в нём безвреден.

## Закрытие разрыва раунда: отчёт есть всегда, а не после повторного запуска

Восстановление работало, но требовало от оператора ещё одного шага именно тогда,
когда он в беде: ночь упала, он пришёл смотреть, что было. Теперь отчёт
обновляется НА КАЖДОМ шоте, помеченный `partial`:

```
  посреди прогона: partial=True, готово 3/8, не начато 5
  после kill -9:   partial=True, готово 3/8
  файл существует БЕЗ повторного запуска: да
```

Запись атомарная (`.part` + rename): падение посреди записи оставляло полуфайл,
потому что rename на POSIX атомарен, а прямая запись — нет.

Цена: **0.74 мс на запись, 0.23 с на серию 314 шотов = 0.009% прогона.** Итоговый
отчёт `partial` не несёт — иначе завершённый прогон читался бы как оборванный.
Восстановление из журнала осталось резервным путём для случая, когда отчёт всё же
не уцелел.

## Итог по линзе

Из четырёх сбоёв один был серьёзным (отчёта нет там, где он и нужен) и закрыт
восстановлением, два давали трейсбек вместо причины и переведены в preflight, один
работал. Отчёт стал устойчивее самого прогона: он собирается из того, что уцелело.
