# Раунд 15 — сборка мастера — линза: resume

Вопрос линзы: **что происходит со сборкой при возобновлении — досчитали один шот,
собираем снова.**

Blender 5.1.1, commit fcb1775. Все числа — замеры на 1080p, 96 кадров на шот.

## Пересобиралось всё, каждый раз

Замер: собрать серию дважды, ничего не меняя.

```
  сборка 1: 0.48s   сборка 2 (всё то же): 0.36s   = 0.75x
  => сегменты пересчитываются (6 шт.)
```

И после правки **одного** шота:

```
  после правки ОДНОГО шота: пересобрано сегментов 6/6
```

Цена на настоящем масштабе (1080p, 96 кадров):

| | |
|---|---|
| один сегмент | 1137 мс |
| серия 314 шотов | 357 с |
| нужно при досчёте одного шота | 0.7 с |
| **лишняя работа на каждый досчёт** | **5.9 минуты** |

Ночь, упавшая трижды, платит этот налог трижды. При этом весь механизм
возобновления построен именно на том, чтобы не делать работу дважды — а сборка
его игнорировала.

Исправлено: сегмент берётся готовым при четырёх условиях, и каждое закрывает свой
способ отдать неверный мастер.

1. **Кадров в сегменте ровно столько, сколько в шоте** — иначе переиспользуется
   обрубок от прерванной сборки.
2. **Сегмент новее всех кадров шота.** Критично: правка тайминга даёт тот же
   набор имён файлов, и сегмент от вчерашних кадров выглядит исправным.
3. **Сегмент новее файла звука** — звук могли перезаписать.
4. **Отпечаток описания совпадает** с тем, что был при сборке сегмента (лежит
   рядом). Изменение разрешения или fps не меняет ни одного имени файла и по
   времени не ловится.

Проверено на четырёх опасных случаях — все пересобирают шот:

```
  кадры sc002 новее сегмента:  пересобран
  разрешение sc002 изменено:   пересобран
  битый сегмент:               пересобран
  звук новее сегмента:         пересобран
```

## Моя же проверка из раунда 14 стоила 117 с на серию

Первый замер переиспользования дал жалкие 2× вместо ожидаемых 100. Стал искать,
куда уходит время при нуле кодирования:

```
  _count_frames по 10 сегментам: 3.73s (373 мс каждый)
  на 314 шотов: 117s — вот куда уходит время
  без -count_frames (из заголовка): 0.26s
```

`-count_frames` **декодирует весь сегмент**. Проверка, которую я добавил в раунде
14 чтобы поймать потерю кадров, сама стоила 117 секунд на серию.

Заголовок надёжен именно для этой задачи — проверил на файле, урезанном до трети:

```
  целый   : заголовок='96'  подсчёт='96'
  обрубок : заголовок=''    подсчёт=''
```

Оба интересующих случая различаются без декодирования. После замены:

```
  первая сборка:  6.2s (было 9.1s)
  повторная:      0.4s = 17x
  на 314 шотов: 195s -> 11s
```

Первая сборка тоже подешевела: 285 с → 195 с.

## Вердикт о целостности переведён на кадры

После раунда 14 `drift +0.023s` остался — и я проверил, откуда:

```
  мастер: 18 кадров, видео 0.750000 s
  18 кадров при 24 fps = 0.750 с — видео верное, +0.023 даёт звук
```

Кадры целы, дрейф целиком от звука (aac округляет вверх). Но пока вердикт
`in_tolerance` считался по длительности, всякий следующий сбой кадров прятался бы
в том же дрейфе — ровно как прожил одиннадцать раундов предыдущий.

Теперь сверяются кадры, а дрейф остаётся справкой:

```
  здоровая:   кадры 24/24, drift +0.023, in_tolerance=True
  битый кадр: кадры 21/24, drift -0.102, in_tolerance=False
```

## report.json не содержал результата сборки

Побочная находка: отчёт писался в `run_episode` — **до** склейки — и при успехе
больше не перезаписывался. Оператор утром открывал файл и не находил ни длины
мастера, ни пропущенных шотов, ни порчи кадров, хотя в терминале это было
напечатано. `PRODUCTION.md` при этом говорит «утром смотреть его, а не закрытый
терминал».

## Итог по линзе

Возобновление сборки не существовало: механизм пропуска готовой работы был у
рендера и не был у склейки. Теперь досчёт одного шота пересобирает один сегмент,
а не 314. Попутно нашлось, что проверка из прошлого раунда стоила больше, чем
экономила, и что отчёт на диске был неполным при успехе.
