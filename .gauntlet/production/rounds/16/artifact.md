# Раунд 16 — сборка мастера — линза: assembly

Вопрос линзы: **швы между шотами видны? порядок верный? звук на месте?
Смотреть на мастер как на ВИДЕО, а не как на файл.**

Blender 5.1.1, commit 9e8d369. Проверял тем, что заметит человек на просмотре.

## Звук шёл впереди картинки всю серию

Спросил контейнер, когда начинается каждый поток:

```
  мастер: video start_time=0.023031   audio start_time=0.000000
```

**Видео стартует на 23 мс позже звука.** У сегментов такого нет:

```
  сегмент sc001: video 0.000000   audio 0.000000
```

Значит расхождение появляется в склейке. Нашёл источник в пакетах сегмента:

```
  звук первые пакеты (pts): ['-0.023220', '0.000000', '0.023220']
```

Первый пакет звука имеет **отрицательный** pts — это priming-кадр aac. Внутри
сегмента он компенсирован, при склейке уезжает в мастер.

Перебрал флаги concat — ни один не помогает:

| вариант | сдвиг |
|---|---|
| как было (`-c copy`) | +23 мс |
| `-avoid_negative_ts make_zero` | +23 мс |
| `-fflags +genpts` | +23 мс |
| перекодировать звук на выходе | +23 мс |
| **PCM в промежуточных сегментах** | **0 мс** |

Причина в том, что источник — сегмент, а не склейка. PCM priming не имеет.

Исправлено: промежуточные сегменты `.mov` с `pcm_s16le`, мастер по-прежнему aac
(кодируется один раз, priming попадает в начало один раз и ничего внутри не
сдвигает). Цена: сегменты 1390 МБ вместо 1280 на серию 314 шотов, времени не
добавляет — 3.5 с против 3.9 на шести шотах.

## Тот же priming объясняет «drift +0.023s»

Это число печаталось в **каждом прогоне всех шестнадцати раундов**. В раунде 14 я
объяснил его округлением aac и перевёл вердикт целостности на кадры, чтобы оно не
маскировало сбои. Теперь оказалось, что оно не погрешность, а тот же priming-кадр:

```
master: /tmp/v16/master.mp4 — 1.0s (expected 1.0s, drift +0.000s)
```

**Дрейф стал ровно нулём.** Два раунда я обходил симптом, не устранив причину.

## Шоты разного размера склеиваются молча

Собрал серию, где один шот 320×180, остальные 320×240:

```
  МАСТЕР: 320,240,24/1,36        ← заголовок
  кадр из sc001: 320,240
  кадр из sc002: 320,180         ← кадр другого размера в том же файле
```

`concat -c copy` менять размер не умеет: берёт заголовок первого сегмента и
дописывает остальные как есть. Что плеер сделает с кадром 320×180 внутри
контейнера 320×240 — не наше решение. Проверки это пропускали: кадров ровно
столько, длина сходится, `in_tolerance=True`.

Самая вероятная причина такого — опечатка в JSON: `[1920, 1800]` вместо
`[1920, 1080]`. Поэтому ловится **до** счёта:

```
  [MIXED_RESOLUTION] shots have different frame sizes — most are 1920x1080,
                     but 1920x1800: sc003
      -> Set the same "resolution" for every shot ...
```

Разный **fps** при этом законен — шот на двойках — и не ругается.

## Что проверил и оказалось целым

| проверка | результат |
|---|---|
| интервалы между кадрами | все ровно 1/24, отклонений 0 |
| форма волны на стыках | гладкая, щелчков нет |
| накопление рассинхрона | +1.9 мс на шот, не суммируется |
| порядок шотов | по раскадровке |
| дубли пакетов звука | нет |

Проверка волны показательна: аудиошвы я искал по интервалам пакетов и получил
88 «разрывов» — это был артефакт моего разбора, а не дефект. Настоящий дефект
(сдвиг 23 мс) нашёлся только когда я спросил `start_time` потоков.

## Побочно: имя сегмента было зашито в двух местах

После смены расширения на `.mov` смоук продолжал искать `segment.mp4` и получал
`None` вместо числа кадров — проверка целостности молча превращалась в «потеряны
все кадры во всех шотах». Имя вынесено в константу.

## Итог по линзе

Мастер был технически корректен и **рассинхронен**: 23 мс между звуком и
картинкой во всей серии, плюс необнаруженная возможность склеить кадры разного
размера. Оба дефекта проходили все проверки, потому что те смотрели на кадры и
длину, а не на взаимное положение потоков.
