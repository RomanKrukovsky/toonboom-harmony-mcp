# Раунд 14 — сборка мастера — линза: resilience

Вопрос линзы: **что происходит при сбое — пропал файл, битый рисунок, кончилось
место. Смотреть на поведение под настоящим сбоем.**

Шесть сбоёв, устроенных руками на живой серии. Blender 5.1.1, commit 8b503b3.

## Найдена молчаливая потеря кадров на ИСПРАВНОЙ серии

Начал с порчи, а нашёл дефект, который не требует никакого сбоя. Считаю кадры в
сегментах здоровой серии:

```
  sc001: PNG 8, в сегменте 7
  sc002: PNG 8, в сегменте 7
  sc003: PNG 8, в сегменте 7
```

**Каждый шот терял последний кадр.** Причина — `-shortest` в команде сегмента:
он обрезает по короткому потоку, и коротким оказывалось видео, а не тишина.
Проверил изолированно:

```
  с -shortest:  PNG 8 → в файле 7
  без -shortest: PNG 8 → в файле 8
```

Масштаб: серия 22 минуты — 314 шотов × 1 кадр = **314 кадров, 13 секунд
анимации**, выпадающих по одному на каждом стыке шотов.

### Почему это прожило одиннадцать раундов

Проверка длины смотрела не туда. `ffprobe` отдаёт длительность **контейнера**, а
её задаёт звук:

```
  сегмент видео: 0.291667 s, 7 кадров
  сегмент звук : 0.332993 s, 16 пакетов
  мастер 1.023s, ожидалось 1.0s, drift +0.023
```

Звук (aac округляет вверх) длиннее видео, поэтому контейнер выходил **длиннее**
ожидаемого. Тот самый `drift +0.023s`, который печатался в каждом прогоне всех
раундов и который я читал как погрешность округления, — это маскировка потери
кадров. Проверка не могла её увидеть **в принципе**: она сверяла длину, а потеря
была в кадрах.

Исправлено: `-shortest` убран, число кадров задано явно через `-frames:v`.
Проверено на живых PNG — 8 из 8 в каждом сегменте.

## Битый PNG проходит в мастер молча

Порча одного кадра из восьми (`write_bytes(b"")` — запись оборвалась):

```
  sc001: кадров в сегменте 8 из 8
  sc002: кадров в сегменте 3 из 8      ← ffmpeg остановился на битом
  sc003: кадров в сегменте 8 из 8
  мастер: 0.815s вместо 1.0s
```

ffmpeg останавливается на нечитаемом кадре и **выходит с кодом 0**. До правки
итог выглядел так:

```
  in_tolerance=False  missing_shots=[]
```

Сказано, ЧТО не так (длина), не сказано ГДЕ. Оператор получает мастер на 0.185 с
короче и должен сам искать, какой из 314 шотов обрублен.

Исправлено: кадры сегмента сверяются с кадрами шота, шот называется поимённо.

```
  DAMAGED ARTWORK: 1 shot(s) lost frames during assembly:
    sc002: 3 of 8 frames — a PNG is missing or unreadable
    -> delete these shot folders and re-run the same command to render them again
```

Код выхода 1 — отдельно от проверки длины, потому что потеря одного кадра из 96
это 0.04 с и в допуск попадает.

## Что и так работало

| сбой | поведение |
|---|---|
| кадр удалён из середины шота | шот признан незавершённым, попал в `missing_shots` |
| каталог шота удалён, журнал `ok` | то же — проверка кадров на диске сработала |
| каталог только для чтения | `PermissionError` с путём |

Первые два — заслуга `shot_is_done()`, которая не доверяет журналу.

## Дефект в подаче ошибок (не закрыт)

Два сбоя дают исключение с обрезанным хвостом ffmpeg вместо причины:

```
RuntimeError: segment failed for sc002: 2, from '/tmp/.../f%04d.png':
  Duration: 00:00:00.17, start: 0.000000, bitrate: N/A
  Stream #0:0: Video: png, rgba(pc, gbr/bt709/iec61966-2 ...
```

426 символов, шот назван, причина (пропавший файл звука) есть — но в середине
технического лога, а не в первой строке. Для `master.mp4 — каталог` хвост
обрезался так, что от причины не осталось ничего: `concat failed: 24 fps, 24 tbr,
12288 tbn Metadata: handler_name : VideoHandler encoder`.

Это тот же класс, что трейсбек вместо инструкции в раунде 8: информация есть,
подача непригодна. Остаётся открытым.

## Итог по линзе

Из шести сбоёв три обрабатывались верно, два молчали (потеря кадров, битый PNG) и
исправлены, один даёт непригодное сообщение. Главная находка — не сбой вообще:
конвейер терял кадр на каждом шоте одиннадцать раундов, и проверка длины
маскировала это положительным дрейфом.
