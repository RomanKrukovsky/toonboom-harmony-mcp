# Раунд 17 — сборка мастера — линза: traceability

Вопрос линзы: **на случайный кадр серии отвечается «какой шот, кто рисовал»?
Смотреть отчёт по кадру, выбранному наугад, а не по удобному.**

Blender 5.1.1, commit 4ec5d3b. Спрашивал про кадры **готового мастера**.

## Реестр отвечал про другой файл

Устроил штатную ситуацию: один шот из пяти упал, шоты разной длины.

```
  длины: [4, 12, 8, 20, 6], упал sc002 (12 кадров)
  в мастере: ['sc001', 'sc003', 'sc004', 'sc005'] = 38 кадров

  записи реестра:            ФАКТИЧЕСКИ в мастере:
    sc001: кадры [1, 4]        sc001: кадры [1, 4]
    sc003: кадры [17, 24]      sc003: кадры [5, 12]
    sc004: кадры [25, 44]      sc004: кадры [13, 32]
    sc005: кадры [45, 50]      sc005: кадры [33, 38]
```

**8 неверных ответов из 12:**

```
    кадр  5: физически sc003, реестр untracked
    кадр 13: физически sc004, реестр untracked
    кадр 22: физически sc004, реестр sc003
    кадр 33: физически sc005, реестр sc004
```

То есть реестр либо не знал кадра, либо называл **чужой шот**. Для юридической
конструкции, ради которой он и заводился, это хуже отсутствия: `untracked`
честно говорит «не знаю», а `sc004` вместо `sc005` — неверный ответ с полной
уверенностью.

## Почему это не заметили в раунде 11

Там я обосновал выбор так: «по ПОЛНОЙ раскадровке, а не по посчитанным шотам:
иначе при досчёте после аварии номера поедут и записи первого прогона станут
указывать не туда».

Обоснование верное — **для досчёта**. И неверное для мастера. Номер кадра значит
две разные вещи:

| нумерация | стабильна при | отвечает на |
|---|---|---|
| по раскадровке | досчёте (шоты добавляются) | где кадр в замысле серии |
| по мастеру | ничём — упавший шот сдвигает всё за ним | где кадр в файле, который смотрят |

Я записал первую и был уверен, что закрыл вопрос. Оператор спрашивает про вторую.

Первые три пробы дали «0 неверных» и почти убедили, что всё в порядке — потому
что я передавал в прогон **урезанный** список шотов, и обе нумерации случайно
совпадали. Дефект открылся только когда прогон увидел полную раскадровку и шот
упал внутри неё.

## Исправление

Нужны **обе** нумерации, каждая на свой вопрос. Раскладка мастера пишется на
сборке — только там известен его состав:

```json
{"action": "master_assembled",
 "detail": {"layout": [{"shot": "sc001", "from": 1, "to": 4},
                       {"shot": "sc003", "from": 5, "to": 12}],
            "missing_shots": ["sc002"], "segments": 4}}
```

`master_frame_report()` берёт **последнюю** запись о сборке: серию собирают заново
после досчёта, и старая раскладка перестаёт описывать файл на диске. Проверено:

```
  после падения двух шотов: мастер 18 кадров, состав [sc001, sc003, sc005], неверных 0
  после досчёта:            мастер 50 кадров, состав все пять,            неверных 0
  цепочка цела: True
```

Раскадровочная адресация не тронута — она отвечает на свой вопрос и нужна
досчёту.

## Полчаса потеряно на `except Exception: pass`

Запись о сборке не появлялась, а ошибки не было. Причина: расчёт раскладки стоял
**после** записи в реестр, и `NameError` съедался обработчиком, поставленным
чтобы «реестр не ронял сборку».

Обработчик правильный по замыслу — падение реестра не должно стоить мастера. Но
`pass` вместо сообщения превратил дефект в невидимку. Теперь причина попадает в
переменную, а регрессия проверяет и порядок строк, и отсутствие молчаливого
`pass`.

## Итог по линзе

Реестр был подключён (раунд 11), цел под `kill -9` (раунд 11), защищён от
подделки (раунд 6) — и отвечал неверно на большинстве кадров готового файла.
Проверка «отчёт по кадру наугад» ловила это только на серии, где шоты разной
длины **и** один не вошёл; на ровных демо-сериях всё выглядело правильно.
