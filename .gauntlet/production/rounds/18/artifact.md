# Раунд 18 — сборка мастера — линза: operability

Вопрос линзы: **человек, не писавший этот код, собирает мастер по документации.
Смотреть на то, что он видит в терминале.**

Blender 5.1.1, commit 4822036. Замыкающий раунд второго оборота линз.

## «Assemble again» было невозможно выполнить

`PRODUCTION.md` трижды говорит оператору «assemble again» / «соберите мастер из
того, что есть»:

```
  Re-run the same command to render them, then assemble again.
  -> restore the file, ... then assemble again
```

В справке такого ключа нет:

```
  --dry-run          preflight only, render nothing
  --no-assemble
  --json             machine-readable report only
```

Есть только «не собирать». Чтобы собрать, надо запустить **полный прогон** — то
есть повторить preflight и учёт готовности всех 314 шотов ради одной склейки. А
если описание серии потерялось, а каталог с кадрами есть:

```
$ python3 episode.py --out /tmp/op18a
episode.py: error: give an episode JSON or --demo
```

Добавлен `--assemble-only`. Замер: **0.5 с** вместо полного прогона.

```
$ python3 episode.py ... --assemble-only
master: /tmp/op18e/master.mp4 — 1.333s (expected 1.333s, drift -0.000s)
  reused 4 segment(s) unchanged since the last assembly
  INCOMPLETE: 1 shot(s) missing from the master: sc003
  Run the same command WITHOUT --assemble-only to render them, then assemble again.
```

Последняя строка важнее, чем в полном прогоне: оператор **явно** попросил не
считать, и подсказка должна сказать, как досчитать.

## Прогноз врал в 11 раз на первой строке

Замер, 30 шотов при 12 воркерах:

```
   10.7s    ok   sc002  1/30  0.38 fps, eta 301.6s     ← факт: 26 с осталось
   11.3s    ok   sc010  7/30  2.55 fps, eta 36.1s
   17.8s    ok   sc013  13/30  2.96 fps, eta 23.0s
   36.8s  rendered 120 frames in 36.54s
```

Формула была `остаток_кадров / наблюдённая_скорость` — верная для
последовательного счёта. При параллельном на первом готовом шоте посчитан
**один**, а работали двенадцать, и скорость измерена по одному.

Это первое число, которое видит оператор. Увидев «eta 301s» на одиннадцатой
секунде прогона, который кончится через 26, он решит, что ночь только началась.

Заменено на волновую оценку: волна = столько шотов, сколько воркеров; время волны
= прошедшее время на число завершённых волн; остаток — целое число волн.

```
   11.7s    ok   sc003  1/30  0.35 fps, eta 34.4s      ← факт: 15 с
   19.4s    ok   sc022  15/30  3.13 fps, eta 19.1s
   24.2s  rendered 120 frames in 23.95s
```

Ошибка 11× → 1.1×.

### Проверил, где это болит на самом деле

Смоделировал ошибку по масштабам, прежде чем чинить:

| шотов | показано | фактически | ошибка |
|---|---|---|---|
| 24 | 37 с | 37 с | 1.0× |
| 100 | 271 с | 296 с | 0.9× |
| 314 | 931 с | 962 с | 1.0× |

На **настоящем** масштабе серии старая формула была верна — дефект жил только в
первых строках, пока завершилась одна волна. Тем не менее правка нужна: именно
первые строки решают, ждать оператору или идти спать.

## Ложная тревога, снятая замером

Первый прогон показал 39 секунд тишины и все десять `ok` одной пачкой — как в
раунде 12, где это было настоящим дефектом буферизации. Проверил журнал:

```
  длительность шота: 34.3-38.1s при 12 воркерах и 10 шотах
```

Десять шотов на двенадцати воркерах идут одновременно и честно кончаются вместе.
Пачка — не дефект вывода, а верное отражение параллельного счёта. Если бы я
доверился внешнему признаку, «исправил» бы работающее.

## Итог по линзе

Сборка была операбельна изнутри полного прогона и неоперабельна отдельно: в
документации описан ход, которого в программе не существовало. Плюс главное
число прогресса врало на порядок именно в тот момент, когда его читают.
