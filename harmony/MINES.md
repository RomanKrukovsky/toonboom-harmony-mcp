# Мины моста Harmony ⇄ MCP

Пронумеровано так же, как ссылки в комментариях `bridge.js`.
Разделено на «обезврежено кодом» и «обезвредить нельзя, только жить с этим».

---

## Обезврежено кодом

**#1. QTcpServer в QtScript Harmony — не гарантирован.**
Экспозиция сетевых Qt-классов в скриптовый движок Harmony не документирована
и различается между сборками. Спека обещала TCP; это была ставка без покрытия.
→ Референсным транспортом сделан **файловый спул + QTimer-поллинг**. Работает
везде, включая `-batch`, переживает падение любой стороны, тривиально
отлаживается (`ls` в спуле показывает всё состояние). Латентность ~40 мс —
на порядок меньше времени любого осмысленного вызова.
TCP остаётся законной оптимизацией — **после** того, как проверен на конкретной
версии, а не до.

**#3. Сборка мусора QObject'ов.**
`QTimer`, созданный в локальной области, умирает вместе с ней, и мост тихо
перестаёт отвечать через несколько секунд после установки — классический
двухчасовой баг.
→ Всё состояние висит на глобальном `MCPB`, созданном присваиванием без `var`.

**#4. Реентрантность.**
`Action.perform`, модальные диалоги, `processEvents` крутят цикл событий, и
таймер выстреливает **внутри** уже работающего обработчика: вложенный
undo-аккумулятор, два ответа на один запрос, гонки в спуле.
→ Флаг `MCPB.inHandler` + клейм запроса переименованием `req-*` → `work-*`.

**#5. Утечка undo-аккумулятора.**
Исключение между `beginUndoRedoAccum` и `endUndoRedoAccum` оставляет
аккумулятор открытым **на всю сессию**: undo-стек художника испорчен до
перезапуска. Это самая дорогая мина в списке, потому что ломает не агента, а
человека, который рядом работает.
→ `withUndo()`: `cancelUndoRedoAccum()` в `catch`, счётчик глубины запрещает
вложенность. Побочный подарок: каждый мутирующий tool call становится
атомарным — упало на середине, откатилось целиком.
Не покрывается: не всё в Harmony undoable. Запись файлов, правка палитр на
диске, `saveAll` откату не подлежат.

**#6. MessageLog нельзя перехватить глобально.**
Хука нет.
→ Пользовательский код компилируется в функцию, у которой `MessageLog` —
**параметр**, затеняющий глобал в пределах всего скрипта. Работает потому, что
нестрогий `eval` видит область вызова; `new Function` тут бы не сработал.
Дыра: код, схвативший ссылку на глобал раньше, утечёт мимо. Приемлемо.

**#7. Движок местами ES3.**
`JSON`, `Object.keys`, `Array.isArray`, `String.trim` могут отсутствовать.
→ Собственные `enc`/`dec` + шимы. Бонус: `enc` экранирует **всё** вне ASCII,
поэтому кириллические имена нод и путей перестают зависеть от того, какой
кодек подсунул `QTextStream`.

**#8. Base64-картинки через транспорт — ошибка спеки.**
`image: base64_png` в исходном документе раздувает полезную нагрузку на треть,
упирается в экспозицию `QByteArray` и вынуждает фреймить мегабайты.
→ Обе стороны на одной машине. PNG пишется на диск, наружу возвращается
**путь**. Модель получает изображение из файла — дешевле, проще, отлаживаемо
глазами.

**#9. Рендер асинхронен.**
`render.renderScene()` возвращается немедленно; результат приходит сигналами
`frameReady` / `renderFinished`. Наивная реализация ждёт в цикле и вешает GUI.
→ Джоб-модель: обработчик возвращает сентинел `DEFERRED`, ответ пишет
`onRenderFinished`, сторож в насосе закрывает зависшую джобу по дедлайну.
Не проверено: путь OpenGL-превью. Обещанного ×50 через `exportOGL` я в
документированном API не нашёл. Практическая замена — `render.setResolution`
вниз до 480–960 px: даёт большую часть выигрыша и точно существует.

**#12/#13. Грязное состояние и точки сохранения.**
Мутации живут в памяти. Всё, что про `.xstage` в git (идея №1) и diff кривых
(№42), требует явного `op:"save"`. Сохранять на каждый вызов — молотить диск и
драться с автосейвом; решение о точках коммита принимает MCP-сервер, не мост.

## Обезвредить нельзя

**#2. Один поток, никакой вытеснимости.**
Скрипты Harmony исполняются на GUI-потоке. `while(true)` от модели морозит
приложение художника намертво, и **изнутри его не остановить**: прервать
QtScript-движок из него самого невозможно.
Что есть:
- `deadline_ms` — это дедлайн **клиента**, а не гарантия. Он означает «мы
  перестали ждать», а не «Harmony жив».
- В песочницу передан кооперативный `budget()`, бросающий `BUDGET_EXCEEDED`.
  Помогает ровно настолько, насколько сгенерированный код его зовёт, — значит,
  требование звать его в каждом цикле идёт в системный промпт агента.
- Единственное настоящее лекарство — убить процесс.

Отсюда практический вывод, который стоит принять до, а не после: **агент не
должен работать в той же копии Harmony, что и человек.** Ферма безголовых
инстансов, сцены из репозитория, художник смотрит результат — не делит с
агентом процесс.

**#10. `harmony_eval` — это удалённое исполнение кода на машине художника.**
Что сделано: локальный спул, обязательный токен (`.token`, 0600), состояние
«разоружён» по умолчанию, ручное вооружение из тулбара, аудит-лог каждой
операции.
Чего не сделано и делать нечего: вооружённый мост исполняет что угодно с
правами пользователя. Любой локальный процесс, дочитавшийся до токена, —
хозяин сцены. Изоляцию даёт периметр (машина, учётка, сеть), а не мост.

**#11. Дрейф API между версиями.**
Сигнатуры `render.*`, `ScriptManager.*`, имена респондеров `Action.perform`
меняются от релиза к релизу.
→ `op:"capabilities"` возвращает версию и результаты **проб** конкретных
функций. MCP-сервер обязан ветвиться по ним, а не по номеру версии, и уж тем
более не по памяти о том, как было в 17-й.

**#14. Заблокированные и read-only сцены.**
Сцена, открытая другим пользователем или без прав на запись, принимает
мутации молча — API не всегда сообщает об отказе. Проверять пробной правкой с
последующим откатом, до начала пакета изменений.

## Порядок ввода в строй

1. `configure.js` + `bridge.js` в пакет, Harmony запускается, `ping` отвечает.
2. `capabilities` — снять карту API конкретной сборки. Всё дальнейшее ветвится
   отсюда.
3. `eval` + `render_frame` — минимальная петля «сделал → посмотрел».
   До этой точки любой тул сверху слеп.
4. Только теперь — `xsheet_*`, `curve_*` и остальной сахар из спеки.

Шаг 3 — водораздел. Всё, что описано в разделах II–VII исходного списка, это
оркестрация поверх него и новых вызовов Harmony не требует.
