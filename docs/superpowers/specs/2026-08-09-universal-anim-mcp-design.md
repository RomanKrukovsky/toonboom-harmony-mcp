# Универсальный MCP-сервер: Harmony и Moho в одном коде

Дата: 2026-08-09
Ветка: `feat/universal-anim-mcp-moho`

## Задача

Проект был MCP-сервером для Toon Boom Harmony. Рядом, в отдельном
репозитории `~/Documents/moho-mcp-server`, жил отдельный MCP-сервер для Moho
Pro 14. Нужен один сервер, обслуживающий оба пакета анимации.

Рабочий сценарий, заданный заказчиком: **человек выбирает свой софт**. Кто
работает в Moho — берёт Moho, кто в Harmony — Harmony. Кросс-приложенческих
потоков нет.

## Ключевое решение: один активный хост

Переменная окружения `ANIM_HOST` (`harmony` | `moho`) при старте выбирает
набор тулов. Отдаётся ровно один набор, никогда оба.

Почему не «все тулы сразу»: 570 тулов Harmony и 59 тулов Moho вместе дают 629
описаний, которые уходят в контекст модели при каждом запуске. Это не только
дорого по токенам — это ухудшает выбор тула: модель выбирает из 629
вариантов вместо 59. Человек всё равно работает в одном приложении, так что
второй набор — чистые накладные расходы.

Опечатка в `ANIM_HOST` **падает на старте**, а не откатывается к Harmony.
Тихий откат — худший вариант: человек просит Moho, получает 570 чужих тулов
и не понимает, почему Moho «не работает».

## Что НЕ делается (осознанно)

- **Нет переноса данных между Moho и Harmony.** Сценарий «риггинг в Moho,
  композит в Harmony» отпадает по условию задачи.
- **Нет общей абстракции** вроде универсального `animation.set_keyframe`,
  который сам решает, куда идти. Moho — это кости и меши, Harmony — граф
  нод. Общая абстракция была бы ложью об обоих.
- **Нет объединения safety/логирования.** Moho привозит свой защитный слой и
  наблюдаемость, они живут рядом с Harmony-механизмами в `src/moho/`.
- **Нет переезда 561 Harmony-тула на новый SDK API.**

## Архитектура

### Расхождение, которое пришлось свести

| | Harmony (этот проект) | Moho (исходный репозиторий) |
| --- | --- | --- |
| SDK API | `new Server()` + `setRequestHandler` | `new McpServer()` + `server.tool()` |
| Определение тула | `defineTool` + Zod-объект | `server.tool(name, desc, shape, handler)` |
| Нейминг | `harmony.scene.open_project` | `document_getInfo` |
| Возврат хендлера | сырые данные | готовый `{ content: [...] }` |

Один процесс — один способ регистрации. Выбран стиль Harmony: переписать 59
тулов дешевле и безопаснее, чем 561 работающий.

### Шов вместо переписывания

Все 59 блоков в `src/moho/tools.ts` имеют одинаковую форму
`registerTool(server, name, desc, shape, handler)`, а вся логика внутри —
вызов `safeSend(...)`, не зависящий от SDK. Поэтому переписан не код тулов,
а **одна обёртка**:

- `src/moho/registry.ts` — класс `MohoToolCollector`, совместимый по вызову с
  `McpServer`, но складывающий тулы в массив.
- `src/moho/mohoTools.ts` — `buildMohoTools()`, собирающий готовый набор.
- `src/moho/toolNames.ts` — карта переименования (59 записей).

### Два дефекта, найденные на шве

Оба легко пропустить: типы совпадают, код собирается в обоих случаях.

1. **Двойная упаковка.** Harmony-хендлер возвращает сырые данные, диспетчер
   сам заворачивает в `content`. Moho-хендлеры возвращают готовый `content`.
   Без распаковки клиент получил бы JSON-строку, внутри которой лежит ещё
   один блок `content` с JSON внутри — данные, нечитаемые для модели.

2. **Проглоченная ошибка.** `errorContent` не бросает, а *возвращает* объект
   с `isError: true`. Для диспетчера Harmony это обычный успех — он ставит
   `isError` только на пойманном исключении. Без обратного превращения в
   исключение отказ Moho («плагин не отвечает», «нет подтверждения
   разрушающей операции») пришёл бы клиенту как успех, и агент продолжил бы
   работу на ложных данных.

Оба исправлены в `adaptHandlerResult` (`src/moho/registry.ts`).

### Инвариант нейминга

Имя MCP-тула **не равно** имени Lua-метода внутри плагина Moho:

| Слой | Пример | Владелец |
| --- | --- | --- |
| Имя MCP-тула | `moho.document.get_info` | этот проект |
| Lua-метод в IPC | `document.getInfo` | плагин Moho |

Переименование тулов не затрагивает строки Lua-методов. Нарушение инварианта
означает, что живой Moho молча перестаёт отвечать, а тесты на моках этого не
замечают.

### Ленивая загрузка Moho

`src/index.ts` подключает Moho динамическим `import` внутри ветки: при
`ANIM_HOST=harmony` IPC-клиент Moho не создаётся и его конфиг не читается.

## Связь с Moho: что человек обязан знать

Мост общается с Moho через файловый spool: TS-сторона пишет
`req_<id>.json`, Lua-плагин внутри Moho забирает и отвечает.

**Опрос внутри Moho работает на событиях перерисовки окна (~4 Гц.)** Когда
окно Moho простаивает и не в фокусе, частота опроса падает и запросы могут не
обрабатываться. Это не дефект реализации, а следствие того, как Moho исполняет
скрипты. Человек должен знать заранее, иначе решит, что «программа повисла».

## Безопасность

- Ввод мыши/клавиатуры и скриншоты **выключены по умолчанию**
  (`MOHO_MCP_ENABLE_UI_AUTOMATION`, `MOHO_MCP_ENABLE_SCREENSHOTS`). Это
  единственный слой, выходящий за пределы IPC и трогающий реальный рабочий
  стол: клик по абсолютным координатам может попасть в любое окно, а
  скриншот утечёт всё видимое на экране.
- Разрушающие операции (удаление кейфреймов, weld точек, сохранение поверх
  файла, batch render) требуют `previewHash` от предварительно построенного
  плана со сроком жизни 60 секунд.
- Журнал транзакций — **аудит, а не механизм отмены**. Отмену дают нативный
  undo Moho, компенсирующие операции и резервные копии файла.

## Проверка

Критерий готовности, согласованный с заказчиком:

1. Сборка и проверка типов проходят.
2. Тесты Moho и Harmony проходят.
3. `ANIM_HOST` реально меняет набор тулов.
4. **Живой Moho отвечает хотя бы на один тул** через новый сервер.

Пункт 4 — главный. Всё остальное проверяется на моках и ничего не говорит о
том, работает ли связь в действительности. В исходном репозитории почти все
тулы имели статус `simulated` — проверены на симулированном IPC, не в живом
приложении.

Возможности Moho внесены в `docs/capability_registry.json` с честными
уровнями проверки: реестр защищён тестовым гейтом, который падает при
завышении уровня без доказательств.

## Известное ограничение

`src/index.ts` статически импортирует все 62 Harmony-набора тулов, поэтому в
режиме `moho` они загружаются в память, хотя в список тулов не попадают и в
контекст модели не уходят. Замер: сборка Moho-набора ~21 мс, Harmony-профиль
~1.4 мс — величины пренебрежимы, поэтому усложнение ради ленивой загрузки
Harmony не оправдано.
