## ОБНОВЛЕНИЕ 2026-08-09, 15:59 — СВЯЗЬ ПОДТВЕРЖДЕНА

`isError: false`. Числа взяты из настоящего документа Moho — это не заглушка.

### Что на самом деле мешало

Шесть причин, и каждая маскировалась под предыдущую: снаружи все давали один
и тот же симптом «таймаут, Moho не отвечает».

**1. `io.popen` не поддерживается в Moho — корневая причина.**
Встроенный Lua возвращает `false, "'popen' not supported"`. Все три
перечисления каталога в плагине шли через него, поэтому `listDir()` **всегда
возвращал пустой список**: плагин физически не мог увидеть ни один запрос,
сколько бы ни опрашивал. Именно это выглядело как «опрос не запущен» и
несколько раз списывалось на ненажатую кнопку в меню. Кнопка ни при чём.
Исправлено: `os.execute` доступен, перечисление идёт через временный
файл-индекс.

**2. Порядок объявлений.** `isSafePath` объявлялась после `listDir`, которая
её вызывает — в Lua это `nil` и падение при первом вызове.

**3. `json` обязан быть глобальным.** `protocol.lua` ждёт global `json`, как
его и грузит `MohoMCP_Server.lua:94`. Тестовая обвязка этого не делала, и
`poll` падал на `json.decode`. Ошибка была в обвязке, не в плагине.

**4. `start()` стирает запросы прошлой сессии.** Запрос, положенный до старта
плагина, удаляется как остаток. Порядок обязателен: сначала плагин, потом вызов.

**5. Два экземпляра Moho конфликтуют** — второй молча не исполнял скрипт.

**6. Без открытого документа — честный отказ** `No active document` (код
`-32010`). Это уже был живой ответ, но данных не давал.

### Как воспроизвести

```bash

pkill -x Moho                     # один экземпляр за раз
/Applications/Moho.app/Contents/MacOS/Moho scripts/moho/serve_headless.lua &
sleep 15                          # плагин должен успеть стартовать
```

`scripts/moho/serve_headless.lua` поднимает мост **без ручного нажатия в
меню**: Moho принимает `.lua` аргументом командной строки и вызывает в нём
`MohoScript(moho)`. Штатный путь через интерфейс (`Scripts -> MohoMCP Server`)
тоже работает и остаётся основным для повседневной работы — скрипт нужен там,
где человека у клавиатуры нет.

### Что это меняет для статусов

Подтверждён **сквозной путь**: MCP-клиент → сервер → файловый обмен →
Lua-плагин внутри Moho → API Moho → ответ обратно.

## Почему Moho не ответил — точная причина

Причина установлена не по симптому, а по файлам состояния самого плагина.

В `moho-plugin/moho_mcp/server.lua`:

- `poll()` **первым делом** пишет `health.json` (строки 468–471), затем
  сканирует `req_*`;
- `server.stop()` пишет `cursor.json` и **удаляет** `health.json` (строки 437–440);
- `poll()` начинается с `if not isRunning then return end` (строка 465).

Наблюдаемое состояние spool:

```
cursor.json   есть  (mtime 02:25:50, дальше не менялся)
health.json   ОТСУТСТВУЕТ
```

Пара «`cursor.json` есть, `health.json` нет» — это подпись **остановленного**
сервера. Если бы `poll()` выполнялся хоть раз, `health.json` был бы создан.
Значит `poll()` выходит на первой строке: `isRunning == false`.

**Итог:** цикл опроса внутри Moho остановлен. Запросы физически некому читать.
Это согласуется с `ARCHITECTURE.md` §2.3 (опрос висит на событиях перерисовки,
~4 Гц), но здесь причина строже: дело не в замедлении простаивающего окна, а в
том, что цикл **вообще не запущен**.

## Как работает `scripts/verify_moho_live.mjs`

Это не мок и не симуляция: поднимается собранный сервер настоящим дочерним
процессом, проводится настоящий MCP-хендшейк по stdio, вызывается настоящий
read-only тул. Единственный источник истины — файл ответа от плагина.

Скрипт **различает исходы**, а не сваливает всё в один таймаут, потому что
отсутствие ответа означает разные вещи в зависимости от того, лежит ли
`req_<id>.json` в spool:

| Код | Исход | Смысл |
| --- | --- | --- |
| 0 | `LIVE_OK` | Живой Moho вернул данные. Связь подтверждена. |
| 3 | `NOT_CONNECTED` | Moho не запущен / плагин не загружен. Связь не проверена. |
| 4 | `SPOOL_STALLED` | Запрос ушёл, ответа нет. Мост исправен, молчит Moho. |
| 5 | `BRIDGE_FAILED` | Мост не смог даже записать запрос. |
| 6 | `HARNESS_FAILED` | Сломался стенд: нет сборки, нет тула, занят spool. |

Три момента, из-за которых наивная версия скрипта врала бы:

- **Спул снимается во время вызова, а не только после.** Мост удаляет
  `req_<id>.json` по своему таймауту (10 с), поэтому пост-фактум запрос уже не
  виден — и исход «Moho молчит» выглядел бы как «мост не записал».
- **Чужая блокировка отделена от отказа Moho.** Брошенный `client_lock.json`
  даёт тот же симптом (`DEGRADED`, нет ответа), но причина к Moho не относится.
  Скрипт проверяет, жив ли держатель: живой — прогон прерывается как невалидный
  (код 6), мёртвый — блокировка убирается.
- **`isError: false` не значит «Moho ответил».** Тулы Moho ловят ошибки IPC и
  возвращают их обычным успешным MCP-результатом со `status: DEGRADED`. Судить
  только по транспорту — значит принять таймаут за успех. Скрипт судит по
  содержимому плюс по состоянию spool.

Запуск:

```bash
node scripts/verify_moho_live.mjs
node scripts/verify_moho_live.mjs --tool moho.document.get_info --timeout 45000
node scripts/verify_moho_live.mjs --ipc-dir /tmp/moho-mcp
```

## Побочные находки

Найдено по ходу проверки. Файлы не мои — **не правил**, передаю владельцам.

1. **Мост не снимает `client_lock.json` при выходе.**
   После каждого прогона блокировка остаётся на диске. `disconnect()` в
   `src/moho/moho-client.ts` удаляет её, но при завершении процесса, видимо, не
   вызывается. Следствие: следующий клиент получает `RESOURCE_LOCKED` и ждёт
   истечения TTL. Наблюдалось трижды: PID 84278, 181, 2517 — все мёртвые.
   → владельцу `src/moho/moho-client.ts` (B2).

2. **`MOHO_MCP_IPC_DIR` из глобального конфига Claude не действует на прогон из
   терминала.** Задание из брифа упоминает `/tmp/moho-mcp`, но переменная живёт
   в конфиге клиента Claude, а не в окружении shell. Прогон честно использовал
   дефолт платформы — `~/Library/Application Support/MohoMCP/ipc`. Обе стороны
   (мост и плагин) резолвили одну и ту же директорию, расхождения нет. Для
   проверки другого spool есть флаг `--ipc-dir`.

3. **Плагин установлен в трёх местах,** с полными копиями в
   `scripts/menu/` и `scripts/menu/MohoMCP/`. На момент проверки обе идентичны
   репозиторию, конфликта нет. Но дублирование означает, что при следующей
   правке плагина обновить нужно обе копии — иначе Moho может загрузить старую.
   → владельцу `scripts/install_moho_plugin.sh` (D3).

4. **`keep-alive.scpt` молча глотает отказ Accessibility.** Всё тело обёрнуто в
   `try` без ветки `on error`, поэтому `osascript` возвращает 0 даже когда
   разбудить окно не удалось. Мост при этом пишет `Keep-alive started`, хотя
   keep-alive фактически не работает. Сообщение вводит в заблуждение.
   → владельцу `src/moho/keep-alive.ts` (B5).

## Чего эта проверка НЕ говорит

Честные границы результата:

- **Не проверено, что плагин корректно обрабатывает запросы.** Ни один запрос
  до обработчика не дошёл. Работоспособность Lua-реализации
  `document.getInfo` остаётся непроверенной.
- **Не проверены остальные 58 тулов.** Проверялся один read-only тул. Даже при
  успехе он подтвердил бы только сам канал, а не все тулы.
- **Не проверены операции записи** и механизм `previewHash` для деструктивных
  операций.
- **Из 4 критериев готовности контракта** этим прогоном закрыты: сборка,
  разделение хостов (59 `moho.*`). **Не закрыт:** «живой Moho отвечает хотя бы
  на один тул». Тесты — вне области этой задачи.
