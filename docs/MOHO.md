# Moho-хост

Сервер обслуживает два пакета анимации: Toon Boom Harmony и Moho Pro 14.
Активный выбирается переменной `ANIM_HOST` при запуске. Этот документ — про
режим `moho`.

## Что нужно сделать, чтобы заработало

```bash
npm run build                      # собрать сервер
bash scripts/install_moho_plugin.sh  # поставить Lua-плагин в Moho
```

Затем в самом Moho: **выбрать инструмент MohoMCP Poller** (или запустить
`Scripts -> MohoMCP Server`). Без этого шага мост не получит ни одного
ответа — почему, объяснено ниже.

Проверка живой связи:

```bash
node scripts/verify_moho_live.mjs
```

## Как устроена связь

Мост не управляет Moho напрямую. Обмен идёт через файлы в общей папке
(spool):

1. Сервер пишет `req_<id>.json` в spool-папку.
2. Lua-плагин **внутри Moho** периодически смотрит папку, забирает файл,
   исполняет метод через Lua API Moho и пишет `resp_<id>.json`.
3. Сервер читает ответ и отдаёт его клиенту.

Папка по умолчанию:

| Система | Путь |
| --- | --- |
| macOS | `~/Library/Application Support/MohoMCP/ipc` |
| Windows | `%LOCALAPPDATA%\MohoMCP\ipc` |
| Linux | `~/.moho_mcp/ipc` |

Переопределяется переменной `MOHO_IPC_DIR` или `MOHO_MCP_IPC_DIR` (проверяются
в этом порядке).

**Важно:** плагин вычисляет папку сам, по той же логике. Он живёт внутри
процесса Moho и переменные окружения сервера не видит. Если задать переменную
только серверу, стороны разойдутся по разным папкам, и плагин **молча**
перестанет отвечать. Поэтому надёжнее не задавать её вовсе и пользоваться
путём по умолчанию.

## Главная особенность: опрос зависит от окна Moho

Плагин опрашивает spool **из цикла перерисовки окна Moho** (~4 раза в
секунду). Отсюда два следствия, которые надо знать заранее:

- **Опрос идёт только когда активен инструмент MohoMCP Poller.** Так прямо
  написано в самом плагине: «The server processes requests while this tool is
  active». Если инструмент не выбран, запросы копятся в папке и никто их не
  читает.
- **Когда окно Moho простаивает или не в фокусе, перерисовки редки** — опрос
  замедляется, и ответ может прийти с задержкой или не прийти вовсе в
  пределах таймаута.

Это не дефект моста, а следствие того, как Moho исполняет скрипты. Признак
проблемы: запрос завершается по таймауту, а в spool-папке файл `health.json`
отсутствует или `cursor.json` не меняется.

## Переменные окружения

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `ANIM_HOST` | `harmony` | Активный хост: `harmony` или `moho` |
| `MOHO_IPC_DIR` | путь выше | Папка обмена (приоритетнее следующей) |
| `MOHO_MCP_IPC_DIR` | — | То же, второе имя |
| `MOHO_MCP_REQUEST_TIMEOUT_MS` | `10000` | Таймаут обычного запроса |
| `MOHO_MCP_RENDER_TIMEOUT_MS` | `30000` | Таймаут рендера |
| `MOHO_MCP_MAX_BATCH_SIZE` | `50` | Предел операций в пакете |
| `MOHO_MCP_PREVIEW_TTL_MS` | `60000` | Срок жизни подтверждения (см. ниже) |
| `MOHO_MCP_LOG_FILE` | — | Файл лога; без него логи только в stderr |
| `MOHO_MCP_ENABLE_SCREENSHOTS` | `false` | Разрешить снимки экрана |
| `MOHO_MCP_ENABLE_UI_AUTOMATION` | `false` | Разрешить ввод мыши и клавиатуры |
| `MOHO_MCP_ENABLE_LEGACY_ALIASES` | `false` | Старые имена тулов (не поддерживаются) |

Опечатка в `ANIM_HOST` **останавливает запуск** с явным сообщением. Это
сделано намеренно: тихий откат к Harmony означал бы, что человек просит Moho,
получает 570 чужих тулов и не понимает, почему Moho «не работает».

## Ввод и снимки экрана выключены

`MOHO_MCP_ENABLE_UI_AUTOMATION` и `MOHO_MCP_ENABLE_SCREENSHOTS` по умолчанию
`false`, и это правильное значение.

Всё остальное общение идёт через файловый обмен и ограничено Lua API Moho.
Эти два флага — единственное, что выходит за пределы обмена и трогает
реальный рабочий стол:

- клик по координатам может попасть **в любое окно**, а не только в Moho;
- отправка клавиш попадает туда, где фокус;
- снимок экрана уносит всё, что на экране видно, включая посторонние окна.

Включайте только осознанно и предпочитайте обычные тулы: они детерминированы,
а нажатие мышью — нет.

## Разрушающие операции требуют подтверждения

Операции, теряющие работу человека, не выполняются с первого вызова. Сначала
строится план, из него берётся `previewHash`, и он передаётся в вызов. Срок
жизни хеша — 60 секунд.

Под подтверждением: удаление кейфреймов, сварка точек меша, удаление слоёв,
сохранение поверх файла, открытие и закрытие документа (теряют несохранённое),
пакетный рендер.

Хеш привязан к **параметрам** операции: подтверждение для «удалить кейфрейм
10» не разрешает удалить кейфрейм 999.

Одно исключение, о котором стоит знать: **одиночный рендер
(`moho.document.render`) подтверждения не требует**, хотя перезаписывает файлы
по указанному пути. Причина не в том, что это безопасно, а в том, что у тула
нет параметра для передачи хеша — пометить его сейчас означало бы сделать
рендер всегда падающим. Путь при этом ограничен разрешёнными папками.
Пакетный рендер (`moho.workflow.batch_render`) подтверждение требует.

### Про отмену — честно

Отмену дают три вещи: **нативный undo Moho**, обратные операции и резервные
копии файла.

Журнал операций в мосте — это **аудит, а не откат**. Он записывает, что было
сделано, и не умеет ничего вернуть. Если операция прошла в Moho, отменять её
нужно средствами Moho.

## Имена тулов

Тулы Moho названы `moho.<область>.<действие>`, Harmony — `harmony.*`.
Пересечений нет.

Внутри плагина имена методов **другие**, и это не опечатка:

| Имя тула (MCP) | Метод внутри Moho |
| --- | --- |
| `moho.document.get_info` | `document.getInfo` |
| `moho.layer.set_transform` | `layer.setTransform` |
| `moho.animation.set_keyframe` | `animation.setKeyframe` |

Первый столбец принадлежит этому проекту, второй — плагину Moho.
Переименование тулов не должно затрагивать второй столбец: плагин знает
только его. Полная карта — в `src/moho/toolNames.ts`.

Области: `document`, `layer`, `bone`, `animation`, `mesh`, `batch`,
`workflow`, `input`, `system`. Всего 59 тулов.

Старые имена вида `moho_doc_info` из отдельного репозитория **не
поддерживаются**: они вводили третью конвенцию поверх двух существующих. При
включённом `MOHO_MCP_ENABLE_LEGACY_ALIASES` они пропускаются с
предупреждением, сервер при этом работает нормально.

## Что проверено, а что нет

Здесь важно не преувеличить.

**Проверено исполнением:**

- переключение хоста: `ANIM_HOST=harmony` даёт 570 тулов, `ANIM_HOST=moho` —
  59, пересечения нет;
- сборка Moho-тулов, схемы и обработчики на месте у всех 59;
- обмен по файлам, разбор протокола, коды ошибок, наблюдаемость — тестами
  (12 наборов, 308 тестов);
- ошибка Moho доходит до клиента **как ошибка**, а не как успех.

**НЕ проверено на живом Moho.** Ни один тул не подтверждён работой в
запущенном приложении в рамках этой интеграции. В исходном репозитории
матрица возможностей содержала 26 пометок `simulated` и 3 `experimental` —
то есть проверку на заглушках и симулированном обмене, а не в Moho.

Текущие уровни в `docs/capability_registry.json` (11 записей Moho):

| Уровень | Записей | Что означает |
| --- | --- | --- |
| `offline_verified` | 3 | Проверено тестами без Moho |
| `contract_verified` | 5 | Контракт компилируется, поведение не доказано |
| `unaudited` | 3 | Не проверено |

В `unaudited` попали воркфлоу-макросы, **защита разрушающих операций** и
ввод/снимки экрана. Последние два — потому что защита без доказательства
работы не защита, а ввод выключен флагами и проверена только сторона отказа.

Реестр защищён тестом: завысить уровень без файлов-доказательств не получится.

## Если не работает

| Симптом | Причина |
| --- | --- |
| Тулов `moho.*` нет в списке | `ANIM_HOST` не задан — взят `harmony` |
| Сервер не запускается | Опечатка в `ANIM_HOST`; текст ошибки назовёт значение |
| Тулы видны, вызовы падают по таймауту | В Moho не выбран инструмент MohoMCP Poller |
| Ответы приходят с большой задержкой | Окно Moho простаивает — опрос замедлен |
| Файл лога не появился | Путь недоступен; причина в stderr при запуске |
| Изменения в коде не видны | Не выполнена `npm run build` |
| В меню Moho два пункта `MohoMCP Server` | Так и должно быть, см. ниже |

Список тулов виден **и без запущенного Moho**: он строится из кода, а не
опросом приложения. Видеть `moho.*` в списке — не значит, что связь есть.

### Файлы в папке обмена

После жёсткого завершения сервера посреди вызова в папке может остаться
`req_<id>.json` — запрос, на который никто не ответил. Убирать вручную не
нужно: при следующем подключении мост подметает файлы старше
`MOHO_MCP_REQUEST_TTL_MS` (30 секунд по умолчанию).

Блокировка `client_lock.json` снимается при выходе, включая Ctrl+C. Если она
всё же осталась (например, процесс убит `SIGKILL`), следующий запуск заберёт
её по истечении `MOHO_MCP_CLIENT_LOCK_TTL_MS` — 5 секунд.

Файл `cursor.json` пишет плагин: там номер последнего обработанного запроса,
сохраняемый между сессиями Moho. Мост его не меняет, но учитывает — счётчик
запросов у моста начинается с 1 при каждом запуске, поэтому ответ из прошлой
сессии мог бы совпасть по номеру с текущим. Такой ответ отклоняется: молча
отдать чужой результат хуже, чем вернуть ошибку.

Отсутствие `health.json` вместе с неподвижным `cursor.json` — признак того,
что опрос внутри Moho не запускался.

### Почему в меню два одинаковых пункта

Установщик кладёт файлы меню **в два места**: `scripts/menu/` и
`scripts/menu/MohoMCP/`. Разные версии Moho сканируют то саму папку `menu`, то
вложенную, и надёжно определить это заранее нельзя.

Обе копии перезаписываются при каждом запуске установщика, поэтому разъехаться
они не могут, а каждая грузит свои модули из своей папки. Работает любой из
пунктов меню. Полный список того, что куда встанет, покажет
`bash scripts/install_moho_plugin.sh --dry-run`.
